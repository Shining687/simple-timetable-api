# Simple Timetable API

A backend for custom timetable events, built with FastAPI, SQLAlchemy, and SQLite. It supports per-user CRUD, overlap checks, title search, weekly event creation, and ICS export. 

## Run locally

Use Python 3.13. Open PowerShell in the project directory and run:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn main:app --reload --port 8001
```

Ensure `python` points to your intended Python installation. Open [API documentation](http://127.0.0.1:8001/docs) to try the endpoints.

Startup creates the `events` table and `timetable.db` in the current working directory. Always start from the project directory to use the same database. Data survives restarts; existing table schemas are not automatically migrated.

## Authentication

All event endpoints require `Authorization: Bearer <token>`. In `/docs`, click **Authorize** and enter a token without the `Bearer` prefix.

| User | Demo token |
| --- | --- |
| Alice | `alice-dev-token` |
| Bob | `bob-dev-token` |

Each user can access only their own events. These fixed tokens provide minimal authentication for this technical test; they are not a production login system.

## API

| Method | Path | Purpose | Success |
| --- | --- | --- | --- |
| POST | `/events` | Create one event | 201 |
| POST | `/events/weekly` | Create a finite batch of weekly events | 201 |
| GET | `/events` | List events, optionally filtered by `keyword` | 200 |
| GET | `/events/{event_id}` | Get one event through event_id| 200 |
| PUT | `/events/{event_id}` | Fully update one event | 200 |
| DELETE | `/events/{event_id}` | Delete one event | 204, no body |
| GET | `/events.ics` | Download all your events as a calendar | 200 |

### Event data

Creation, full updates, and weekly creation use the same JSON body:

```json
{
  "title": "Team meeting",
  "description": "Discuss project progress",
  "location": "Library",
  "starts_at": "2026-09-25T14:00:00",
  "ends_at": "2026-09-25T15:00:00"
}
```

- `title`, `starts_at`, and `ends_at` are required; the title must contain at least one character.
- `description` and `location` are optional and nullable. Omitting them in a PUT request clears them.
- Times must have no timezone suffix: do not add `Z` or `+08:00`. They are stored as entered, with Hong Kong local time as the usage convention.
- Responses include these fields plus an integer `id` generated by the database and an `owner_id` determined by authentication. Creation, retrieval, and updates return one object; lists and weekly creation return arrays.

### Time conflicts

Start time must be earlier than end time. Creation and updates reject overlaps with the same user's other events. Updates exclude the event being edited. Adjacent events, such as 14:00-15:00 and 15:00-16:00, are allowed. Different users may use the same times.

Errors return a `detail` field: `401` for invalid tokens, `404` for missing or other users' events, `409` for overlaps, and `422` for invalid input. Validation error details may be a list.

### Title search

`GET /events?keyword=meeting` matches titles containing the keyword, ignoring English letter case. Description and location are not searched. Surrounding whitespace is removed; an omitted or blank keyword returns all your events. Results are sorted by start time and id; no matches returns `[]`.

### Weekly events

`POST /events/weekly?repeat_count=3` uses the first occurrence's event body and creates three events, seven days apart. The count includes the first occurrence, defaults to 4, and must be between 1 and 20.

Every occurrence is checked before the batch is saved. If any conflicts, none are created. For multiple occurrences, an event cannot last longer than seven days. Each generated event has its own id and can be edited or deleted individually; there is no linked series or whole-series update.

### Calendar export

Download with an authenticated request:

```powershell
Invoke-WebRequest -Uri http://127.0.0.1:8001/events.ics -Headers @{Authorization = "Bearer alice-dev-token"} -OutFile events.ics
```

The file contains all events belonging to the current user. Event times are exported as floating local times: 14:00 stays 14:00 in the importing calendar's local timezone. The generation timestamp uses UTC. This is a snapshot, not automatic synchronization.

## Code structure

| File | Responsibility |
| --- | --- |
| `database.py` | SQLite engine, model base, and one session per request |
| `models.py` | Event table and shared request schema |
| `auth.py` | Resolve the user from a Bearer token |
| `event_checks.py` | Shared time-order and overlap checks |
| `main.py` | Startup table creation, CRUD, search, and weekly creation |
| `calendar_export.py` | ICS export router |
| `smoke_test.py` | Automated API checks using a temporary database |

FastAPI resolves authentication and database dependencies, validates input, and runs the endpoint. Write endpoints check conflicts before changing records and commit explicitly. Sessions close after use. Database endpoints use synchronous functions to match the synchronous SQLAlchemy sessions.

## Tests

```powershell
.\.venv\Scripts\python.exe -m pip install httpx==0.28.1
.\.venv\Scripts\python.exe smoke_test.py
```

Tests cover CRUD, persistence, authentication, user isolation, time conflicts and boundaries, keyword search, ICS export, and weekly batches, including rejection without partial saves. Tests use a temporary database and do not modify `timetable.db`.

## Run with Docker

Build the image from the project directory:

```powershell
docker build -t simple-timetable-api .
```

Start the API on port 8000 and keep the SQLite database on the host:

```powershell
docker run --name simple-timetable-api-container `
  -p 8000:8000 `
  -v "${PWD}\timetable.db:/app/timetable.db" `
  simple-timetable-api
```

Open <http://127.0.0.1:8000/docs> for the Swagger UI. Stop the container with `docker stop simple-timetable-api-container` and start it again with `docker start simple-timetable-api-container`.

## Current limitations

- Overlap checks query before writing; concurrent requests can still race.
- ICS UIDs use database integer ids, which may collide across databases or when ids are reused. Repeated imports may create duplicates depending on the calendar application.
- Time-range filtering, pagination, general recurrence rules, and MCP are not implemented yet.
